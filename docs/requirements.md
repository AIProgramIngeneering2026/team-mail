# Требования

## Жизненный цикл Job
Job — это одно уведомление.
Состояния: принято, отправляется, доставлено, не доставлено, отменено.

Разрешённые переходы:
- принято → отправляется
- отправляется → доставлено
- отправляется → не доставлено (после N повторов)
- принято → отменено
- отправляется → отменено

Запрещены: доставлено → отправляется, отменено → отправляется.

## Сценарий 1. Успешная отправка (основной)
Цель: клиент хочет, чтобы получатель получил сообщение.
Участник: клиентское приложение.

Основной поток:
1. Клиент отправляет запрос: получатель, канал, текст.
2. Система создаёт Job в состоянии «принято».
3. Исполнитель канала отправляет сообщение, Job переходит в «отправляется».
4. Канал подтверждает доставку, Job становится «доставлено».
5. Клиент по id Job получает статус.

Критерии приёмки:
- Дано: получатель с email, канал доступен.
  Когда: клиент отправляет запрос.
  Тогда: статус Job «доставлено», письмо отправлено ровно одно.

## Сценарий 2. Таймаут канала (ошибочный)
Цель: не потерять сообщение при сбое канала.
Участник: клиентское приложение.

Основной поток:
1. Клиент отправляет запрос.
2. Канал не отвечает.
3. Система повторяет попытку.
4. Попытки закончились, Job переходит в «не доставлено».

Критерии приёмки:
- Дано: канал не отвечает.
  Когда: клиент отправляет запрос.
  Тогда: попыток не больше N, статус «не доставлено», причина «timeout».

## Сценарий 3. Двойной запрос (ошибочный)
Цель: не отправить одно сообщение дважды.
Участник: клиентское приложение.

Основной поток:
1. Клиент отправляет запрос с идентификатором.
2. Из-за сбоя сети клиент повторяет тот же запрос.

Критерии приёмки:
- Дано: уже есть Job с таким идентификатором.
  Когда: приходит запрос с тем же идентификатором.
  Тогда: новый Job не создаётся, возвращается существующий.

## Сценарий 4. Отмена посередине
Цель: остановить ненужную отправку.
Участник: клиентское приложение.

Основной поток:
1. Job находится в состоянии «отправляется».
2. Клиент отправляет отмену.
3. Система прекращает повторные попытки.

Критерии приёмки:
- Дано: Job «отправляется».
  Когда: клиент отменяет.
  Тогда: статус «отменено», новых попыток нет.
- Дано: Job «доставлено».
  Когда: клиент отменяет.
  Тогда: отказ, статус не меняется.

## Сценарий 5. Неверные входные данные (ошибочный)
Цель: отклонять некорректные запросы сразу.
Участник: клиентское приложение.

Основной поток:
1. Клиент отправляет запрос с пустым адресом, неподдерживаемым каналом или пустым текстом.
2. Система проверяет вход до создания Job.

Критерии приёмки:
- Дано: адрес пустой или не похож на email.
  Когда: клиент отправляет запрос.
  Тогда: ошибка валидации с понятным текстом, Job не создаётся.
- Дано: указан канал, которого нет в системе.
  Когда: клиент отправляет запрос.
  Тогда: ошибка «канал не поддерживается», Job не создаётся.

## Что предложил ИИ

Промпт:

> Основной сценарий сервиса уведомлений: клиент отправляет запрос (получатель, канал, текст), система создаёт Job «принято», исполнитель канала отправляет сообщение, Job становится «отправляется», затем «доставлено». Найди ещё 3 способа сломать этот сценарий, которых нет в списке: таймаут, двойной запрос, отмена посередине, неверный адрес. Для каждого опиши условие и ожидаемое поведение системы.

| Предложение ИИ | Решение | Почему |
|---|---|---|
| Канал не поддерживается или отключён | принято | Простая проверка на входе, добавлено в сценарий 5 |
| Пустое или слишком длинное сообщение | принято | Защищает от неполных сообщений, проверяем до создания Job |
| Падение между отправкой и записью статуса | принято, но позже | Важный случай, но сложный: вынесем в отдельную issue и сделаем после базового каркаса |
